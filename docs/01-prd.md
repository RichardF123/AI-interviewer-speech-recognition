# PRD：AI 面试官语音功能

## 用户角色

- 候选人：通过语音回答面试问题，期望系统听得准、响应快、可自然打断。
- AI 面试官：理解候选人回答，生成追问、澄清、下一题和结束语。
- 招聘方/评估系统：查看转写、评分依据、音频回放和质量指标。
- 研发/运维：接入 provider、排查延迟与错误、管理数据合规。

## 核心用户故事

- 作为候选人，我希望直接说话回答问题，不需要手动输入。
- 作为候选人，我希望 AI 面试官不要在我还没说完时抢话。
- 作为候选人，我希望我开口打断时，AI 面试官能立刻停下。
- 作为招聘方，我希望看到候选人回答文本、原始音频和系统追问依据。
- 作为运维，我希望知道每轮语音链路的延迟、错误和断连情况。

## 语音输入需求

- 浏览器采集麦克风音频，并持续发送 `audio.chunk`。
- 优先使用 PCM16、16kHz、mono；若浏览器使用 WebM/Opus，后端需要转码后再送 STT。
- 前端展示 `stt.partial` 作为实时字幕。
- `stt.partial` 不进入 LLM。
- `stt.final` 经过规范化后进入 LLM。
- 支持热词扩展，例如岗位名、技术栈、公司名。
- 支持噪声环境下的基础鲁棒性提示，例如提示候选人靠近麦克风。

## 语音输出需求

- LLM 回复必须转为适合朗读的短句。
- TTS 默认语气为专业、温和、清晰、语速中等偏慢。
- 支持首句或短句流式合成，降低候选人等待时间。
- 避免朗读 Markdown、复杂编号、代码块、不可读符号。
- 前端使用播放队列按序播放 `tts.audio`。

## 打断需求

- 当前端检测到候选人开口，立即停止本地播放队列。
- 前端发送 `control.interrupt` 到后端。
- 后端取消当前 turn 的 TTS 合成任务和未发送音频。
- 后端记录被打断的 turn、触发时间和打断响应延迟。
- 面试官恢复时应简短确认，例如“好的，我先听你补充。”

## 日志与复核需求

- 保存会话事件流：音频片段索引、STT partial/final、LLM 输入输出、TTS 文本、指标和错误。
- 可选保存原始音频或分段音频，保存前必须获得候选人授权。
- 抽样音频可由 faster-whisper 或 FunASR 离线复核，计算 CER/WER。
- 支持按 session、turn、utterance 查询。

## 延迟体验要求

- STT partial 首字目标：小于 800ms。
- STT final 目标：候选人停顿后 700-1200ms 内提交。
- LLM 首 token 目标：小于 1000ms。
- TTS 首包目标：小于 1000ms。
- 端到端首包播放目标：候选人说完后 2-3 秒内。
- 打断停止播放目标：前端 200ms 内停止，后端 500ms 内确认取消。

## MVP 验收口径

- 能创建面试 session。
- 能建立 WebSocket 语音会话。
- 前端能发送音频 chunk 并接收字幕、面试官文本和音频事件。
- mock STT/TTS 可完成端到端联调。
- 真实 provider 配置位清晰，无真实密钥。
- `stt.partial` 不进入 LLM 的规则在代码和文档中一致。
- 能记录 turn 级延迟指标。
- 能处理 `control.interrupt` 并清理播放/合成队列。

## 非功能需求

- 可用性：provider 故障时支持降级到文本模式或 mock 提示。
- 隐私：候选人授权、音频加密存储、到期删除。
- 审计：关键事件和评分依据可回放。
- 可观测性：链路指标、错误码、WebSocket 断连率可查看。
- 扩展性：STT/TTS provider 可切换，业务层无厂商耦合。
